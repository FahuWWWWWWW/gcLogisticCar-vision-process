# 上下位机串口通信协议与测试指南

> 本文档用于定义树莓派/PC (上位机) 与 STM32/Arduino (下位机) 之间通信成功与失败的判断标准、测试方法以及故障排查指南。供视觉开发人员与嵌入式开发人员联调使用。

---

## 1. 通讯成功/失败的定义与判定标准

为了保证搬运任务的顺利进行，通信状态被分为三个级别：**物理链路连接、控制信令交互、业务数据合法**。

### 1.1 物理链路级 (Connection Layer)

*   **判定为【成功】**：
    *   上位机能够成功打开配置文件指定串口（如 `COM3` 或 `/dev/ttyUSB0`）。
    *   下位机在连线接入后，串口线上的 DTR/RTS 信号触发或串口正常接收到树莓派的包（TX/RX 指示灯闪烁）。
*   **判定为【失败】**：
    *   上位机日志输出 `[ERROR] - serial_comm.py:39 - 串口连接失败: ...`。
    *   由于权限不足（Linux 下未加 `dialout` 用户组）或端口被占用导致启动闪退。

### 1.2 控制信令级 (Message Layer)

*   **判定为【成功】**：
    *   双方发送的每一包数据都以换行符 `\n` 结尾，且为标准的 JSON 格式。
    *   上位机成功解析下位机发来的指令，日志打印 `收到下位机任务指令: <TYPE>`。
    *   当下位机发来畸变/非法 JSON 时，上位机不会死机或闪退，能够安全捕获并打印警告 `接收到非 JSON 格式数据: ...`。
*   **判定为【失败】**：
    *   单片机发送数据后上位机毫无反应（多为未加 `\n` 换行符，导致树莓派接收缓冲区一直在等待数据包结束）。
    *   单片机端因 JSON 解析库（如 `ArduinoJson`）内存分配不足，导致解析上位机回传的坐标数据时返回 `InvalidInput` 或直接复位。

### 1.3 业务逻辑级 (Business Layer)

*   **判定为【成功】**：
    *   **扫码状态下**：树莓派成功解出二维码，发送 `QR_RESULT` 帧；单片机成功解析并执行相应搬运流程。
    *   **找色块/找圆环状态下**：树莓派计算出物理坐标并发送 `COORD_RESULT` 帧。
*   **判定为【失败】**：
    *   树莓派超过指定时间（例如 5 秒）仍未检测到目标，发送 `ERROR` 帧（`{"msg": "not_found"}`）。
    *   下位机接收到的坐标值超出了赛场的合理物理范围（如计算出负数或大于赛场尺寸的值），判定为标定失效。

## 2. 通讯成败判定表

| 通信方向 | 期望发送的 JSON 载荷 (Data) | 成功判定标准 | 失败判定标准 | 异常处理机制 |
| :--- | :--- | :--- | :--- | :--- |
| **下位机 ➜ 上位机**<br>(触发扫码) | `{"type": "QR_READ", "data": {}}` | 上位机进入 `QR_READ` 状态，镜头绿灯闪烁或启动画面显示 `State: QR_READ`。 | 上位机状态仍为 `IDLE`。 | 下位机若 500ms 内未收到上位机的心跳/确认，需重新发送。 |
| **下位机 ➜ 上位机**<br>(寻找红色块) | `{"type": "FIND_BLOCK", "data": {"color": "red"}}` | 上位机进入 `FIND_BLOCK` 状态，画面锁定红色最大色块，开始计算物理坐标。 | 提示 `找不到 red_cube 的 LAB 阈值` 或状态无变化。 | 检查 `config/color_config.yaml` 颜色配置拼写。 |
| **上位机 ➜ 下位机**<br>(返回扫码结果) | `{"type": "QR_RESULT", "data": {"data": "task_str"}}` | 下位机收到指令，提取出 `data` 字符串，且成功将其存入任务数组。 | 下位机解析失败，或获取的字符串为空。 | 下位机向树莓派重新发送 `QR_READ` 索要结果。 |
| **上位机 ➜ 下位机**<br>(返回物理坐标) | `{"type": "COORD_RESULT", "data": {"x": 120.5, "y": 350.1}}` | 下位机收到 `x` 和 `y` 物理坐标（毫米），步进电机/舵机精准移动到目标上方。 | 下位机收到坐标后死机；或者机械臂移动发生剧烈偏差。 | 1. 确认标定矩阵有效性。<br>2. 下位机滤除异常坐标。 |
| **上位机 ➜ 下位机**<br>(返回识别失败) | `{"type": "ERROR", "data": {"msg": "not_found"}}` | 下位机收到失败帧，执行“扫场模式”（如移动机械臂扩大视野或再次触发）。 | 下位机无限期挂起等待。 | 下位机需设置单次任务超时时间。 |

## 3. 联调测试步骤流程

联调前，建议分两步走：**纯模拟测试** 与 **串口环路实机测试**。

### 步骤一：上位机键盘模拟测试（验证视觉与坐标计算）
1. 在 PC 或树莓派上运行：`python main.py`。
2. 确保已开启调试模式（未连接下位机时自动启用）。
3. **按下键盘 `1` 键**：模拟单片机要求扫码。出示二维码，观察控制台是否打印 `扫码成功` 且程序切回 `IDLE`。
4. **按下键盘 `2` 键**：模拟单片机要求寻找红色块。在视野中放入红块，检查是否正确框选并打印出映射后的 X, Y 物理坐标。
5. **按下键盘 `3` 键**：模拟单片机要求找圆环。

### 步骤二：下位机伪串口测试（验证单片机解析）
下位机同学可以使用 USB 转 TTL 串口线连接电脑，打开**串口助手**，手动向上位机发送报文：
```json
{"type": "QR_READ", "data": {}}
```
*(注意：发送时串口助手必须勾选 “发送新行” 或手动输入 `\n`)*。
观察串口助手的接收窗口是否能够正常收到上位机回传的：
```json
{"ver": "1.0.0", "type": "QR_RESULT", "seq": 1, "ts": 1751374800000, "data": {"data": "XXX"}}
```

## 4. 常见排坚指南 (Troubleshooting)

### Q1: 树莓派程序启动正常，单片机发送数据后，树莓派日志完全没有“收到任务”的提示？
*   **A**：极大概率是单片机发送的串口数据**结尾没有加换行符 `\n` (ASCII: 10)**。上位机串口读取线程 `_read_loop` 会一直等待换行符出现才把这一帧切下来解析。
*   **解决方法**：在单片机发送的串口字符串末尾强制追加 `\n`。对于 Arduino 平台，请使用 `Serial.println(json_str)` 而非 `Serial.print`。

### Q2: 串口连接不上，报错 `could not open port`？
*   **A**：
    1. 端口名配置错误：Windows 下请确认是 `COM3` / `COM4` 等；树莓派/Linux 下通常为 `/dev/ttyUSB0` 或 `/dev/ttyACM0`。请在 `config/serial_config.yaml` 中进行对应修改。
    2. 权限不足：在 Linux/树莓派下，运行 `sudo usermod -a -G dialout $USER` 然后重启系统，以获取免 sudo 读写串口的权限。

### Q3: 为什么单片机接收到 JSON 数据后，解析出的坐标数据总是随机的零或者直接死机？
*   **A**：单片机（尤其是使用 C++ 的 `ArduinoJson` 库）通常采用固定大小的内存池（`StaticJsonDocument`）。如果内存池分配得太小（例如少于 128 字节），当读取到较长的 JSON 包时会发生内存溢出。
*   **解决方法**：建议单片机开发者将 `JsonDocument` 的容量设置在 `256` 字节以上，防止溢出。
